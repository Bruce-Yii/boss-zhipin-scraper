# 审查 brief：实现正确性（独立第三方）

> 固定模板（data/audit_briefs/）。不要临场改写——它本身是被 review 的对象。

## 你的角色
独立第三方代码审计员，**没有参与实现**。只做审计，**不要改任何代码**。

## 你要回答的唯一问题
> **哪里会让产出错、丢、不一致，或悄悄损坏用户数据？**

## 审计对象
本次改动的代码（范围在任务里给）+ 关键调用链（不要只看改动的那几行）。

## 必须做的
1. **读调用链，不只读 diff**：改一个函数，要看它的**所有调用方**（同一个参数在不同入口
   行为是否一致？控制台口径与落盘口径是否一致？）。
2. **落盘 vs 内存**：过滤/裁剪/去重这类操作，是否**只改了内存副本**而落盘文件仍是全量？
   （2026-10-22 实测：过滤只改内存 → 控制台说"丢弃 N 条"，落盘 JSON/CSV 仍是全量。）
3. **合并路径**：跨文件/跨 run 合并时，被排除的旧数据会不会被复活？
4. **失败路径**：异常、缺文件、空结果、并发冲突，会不会产出"看起来成功但内容是空"的结果？
   退出码对不对？
5. **并发与状态文件**：跨进程的读改写有没有文件锁？Windows 上 `os.replace` 会不会抛
   `PermissionError`？宽泛的 `except` 会不会把"并发冲突"误报成"浏览器故障"？
6. **状态泄漏**：永久性状态（坏页台账、黑名单）有没有 TTL？把**瞬时**失败当永久失败处理了吗？
   文档里承诺的逃生口（比如某个重试参数）是不是真的生效？
7. **确定性**：同样的输入两次跑出来的结果一样吗？有没有用 `hash()` 这类进程随机的东西？
8. **红线**：平台凭据（securityId/cookie/token）有没有可能落盘？

## 输出要求
- 每条：**文件:行号 → 为什么是问题 → 在什么情况下真会发生**（不要报纯理论问题）。
- 怎么验证的（读代码 / 跑只读探针 / 跑现有测试）；探针脚本只能写到 temp 下。
- 按严重度：会让用户拿到错数据 > 静默丢数据 > 体验/维护性。
- 明确说清**哪些区域是干净的**。
