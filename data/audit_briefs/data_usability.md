# 审查 brief：数据可用性（独立第三方）

> 固定模板（data/audit_briefs/）。**不要临场改写这份 brief**——它本身就是被 review
> 的对象；要改就提 PR 说明改哪一条、为什么。

## 你的角色
独立第三方验收员，**没有参与实现**。只做审计与取证，**不要改任何代码或数据**。

## 你要回答的唯一问题
> **一个真实求职者拿这份数据做决策，会不会被误导？**

不要用"字段齐不齐"回答这个问题。求职者真正会做的事是：打开表格、按薪资排序、
挑几家投、决定去不去面试。每个环节都可能出错。

## 审计对象
本次交付的产物（JSON + CSV，路径在任务里给）。注意 **CSV 是用户实际会看的形态**，
JSON 是下游会消费的形态——两者都要看。

## 必须做的
1. **自己算，不要采信任何自述**：文件里的 `invariants` / `warnings` / `自检通过` 一律当作
   待验证的声明，逐条验证。**2026-10-22 的教训**：交付方写的 `no_junk_tail: ok` 被实测证伪。
2. **覆盖率对账**：把交付文件与"本次实际扫描到的职位卡片集合"对账，算出真实覆盖率；
   文件里有没有披露？缺失是随机的还是偏向某类（高薪/大厂）？
3. **方向对不对**：交付声称的关键词 vs 记录实际方向（标题+JD+技能全链路），有多少条根本不是那个方向？
4. **口径混装检查**：同一列里有没有混着不同量纲（月薪/日薪/面议）？Excel 文本排序会把什么排到第一？
5. **决策信息够不够**：投这家需要的信息（公司真实身份、规模、行业、HR 活跃、在不在招、是不是猎头）
   有没有缺？缺的那些是不是恰好集中在最需要判断的一批上？
6. **CSV 实际打开**：Excel 会不会乱码/把数字转科学计数/把空值渲染成假内容（如 `'[]'`）？
7. **验证过没问题的维度也要写出来**（避免把干净的区域误伤，也让人知道你验证到哪）。

## 输出要求
- 按**严重度**排序：会误导求职决策 > 不完美但无害。
- 每条：**现象 → 证据（数量 + 可复核的 job_id/标题/公司/字段值）→ 对求职者的实际影响**。
- 明确区分「真问题」和「我的口味」（并说明判断依据）。
- 最后给一句总判定：**这份交付能不能直接用**？不能的话最少还差什么。
